02Was auf dem Tisch liegt

Sieben Dateien, eine Steigerung

Die Präsentation vergleicht die beiden markierten Dateien. Sie lösen dieselbe Aufgabe mit demselben Tool — unterschiedlich ist nur der Transport.

03Die Konstante

Was sich nicht ändert, ist der Punkt

Wrapper A third_agent.py Schema · Aufruf · Fehlerbehandlung. Keine Fachlogik.
Wrapper B fourth_agent.py Schema · Aufruf · Fehlerbehandlung. Keine Fachlogik.
importiert ↓importiert ↓
Fachlogik, unverändert confidence.py → assess() ADR-008, fail-closed. Standardbibliothek, keine Projekt-Importe, kein I/O. test_confidence.py deckt beide Anbindungen ab.

Weil der Wrapper keine Logik enthält, kostet der Wechsel SDK → OpenAI nichts an Fachlogik. Genau dafür trennt man Logik vom Transport.

04Unterschied 1 · Die Schleife

Wer hält die Agent-Schleife

SDKthird_agent.py

Das SDK hält sie.

async for msg in query(prompt=PROMPTS[case], options=opts):
    if isinstance(msg, AssistantMessage):

            if isinstance(block, ToolUseBlock):

Du konsumierst einen Strom typisierter Nachrichten. Tool-Aufruf, Ergebnis und Verlauf laufen unter der Oberfläche.

Rohbaufourth_agent.py

Du hältst sie.

for turn in range(1, MAX_TURNS + 1):

Generiert oder von Hand geschrieben

Typ, Beschreibung und JSON-Schema kommen aus einer Quelle. Eine Stelle zu pflegen.

Rohbau~40 Zeilen JSON
TOOLS = [{"type": "function", "function": {
  "name": "confidence_score",

Genau das geht über die Leitung. Doppelt gepflegt — Signatur hier, Schema dort.

Identisch in beiden: der description-Text. Er ist der Teil, der das Modell steuert — und er überträgt sich wörtlich.

06Unterschied 3 · Registrierung

MCP-Server gegen Handler-Dictionary

SDKIn-Process-MCP
learnflow = create_sdk_mcp_server(
    name="learnflow", version="1.0.0",
    tools=[confidence_score])

opts = ClaudeAgentOptions(
    mcp_servers={"learnflow": learnflow},
    allowed_tools=["mcp__learnflow__confidence_score"],
    #              mcp__<schlüssel>__<tool-name>
)

allowed_tools ist eine echte Schranke — was nicht drinsteht, existiert für das Modell nicht.

RohbauName → Funktion
HANDLERS = {"confidence_score": run_confidence_score}

def dispatch(name, arguments_json):
    handler = HANDLERS.get(name)
    if handler is None:
        return json.dumps({"error": f"unbekannt: {name}"})
    try:
        arguments = json.loads(arguments_json)
        return json.dumps(handler(**arguments))
    except (json.JSONDecodeError, TypeError) as exc:
        return json.dumps({"error": f"{exc}"})

Trivial — aber du schreibst es. Und es gibt nichts zu beschränken: was im Array steht, ist erlaubt.

Stille Fehlerquelle

Ein Vertipper in mcp__<schlüssel>__<tool> wirft keinen Fehler — das Tool wird stumm nie aufgerufen. Deshalb prüft smoke_third_agent.py genau diesen Namensvertrag, bevor ein bezahlter Lauf startet.

07Unterschied 4 · Ergebnis & Verlauf

Wie das Ergebnis zurückkommt

SDKcontent-Blöcke
return {"content": [{"type": "text",
                "text": json.dumps(payload)}]}

# Fehlerfall — das Modell darf korrigieren:
return {
    "content": [{"type": "text",
                 "text": f"Ungültige Parameter: {exc}"}],
    "is_error": True,
}

Zuordnung und Verlauf macht das SDK. Fehler haben ein eigenes Feld.

Rohbaurole: tool
for call in message.tool_calls:
    content = dispatch(call.function.name,
                       call.function.arguments)
    messages.append({
        "role": "tool",
        "tool_call_id": call.id,   # so ordnet das
        "content": content,      # Modell zu
    })

Zuordnung über die ID. Fehler sind ein normales Ergebnis — als JSON mit error-Schlüssel.

Beim Anthropic-Protokoll wäre das stattdessen ein tool_result-Block in einer User-Nachricht. Zwei Protokolle, dieselbe Idee — das SDK versteckt beide.

08Unterschied 5 · Leitplanken

Was den Lauf stoppt, bevor er teuer wird

SDKOptionen
opts = ClaudeAgentOptions(
    model="claude-sonnet-4-6",
    max_turns=5,
    max_budget_usd=0.20,   # hart: bricht ab
)

# Kosten kommen fertig:
elif isinstance(msg, ResultMessage):
    print(f"${msg.total_cost_usd:.4f}")

Turns und Geld sind begrenzt. Beides eine Zeile Konfiguration.

RohbauKonstante
MAX_TURNS = 5   # nur Turns, kein Budget

try:
    cost += litellm.completion_cost(response)
except Exception:
    # Schätzung fehlt für manche Modelle —
    # kein Grund abzubrechen.
    pass

Kosten werden geschätzt, nicht begrenzt. Die Schätzung darf ausfallen.

Konsequenz

Im Rohbau können fünf teure Turns durchlaufen; die Kosten erfährst du danach. Wer dort eine harte Obergrenze will, baut sie selbst — etwa Abbruch, sobald cost eine Schwelle reisst.

10Bilanz

Vorteile und Nachteile

SDKthird_agent.py

Dafür

  • Schleife, Verlauf und Kostenzählung geschenkt
  • Schema aus der Signatur — keine Doppelpflege
  • Hartes Budget-Limit statt Schätzung
  • Freigabeliste als Sicherheitsgrenze
  • Typisierter Strom macht Debuggen sichtbar

Dagegen

  • An Claude gebunden — kollidiert mit ADR-004
  • Zusätzliche Laufzeit-Abhängigkeit
  • Verlauf ist nicht dein Objekt: kürzen, injizieren, persistieren geht nicht ohne Weiteres
  • Stille Fehlerquelle im mcp__-Namen
  • Verhalten der Schleife bleibt Blackbox
Rohbaufourth_agent.py

Dafür

  • Provider-frei — passt exakt auf den LearnFlow-Backend-Stack
  • Voller Zugriff auf messages: kürzen, speichern, in die DB legen
  • Nichts Verborgenes — jeder Schritt steht da
  • Reine Python-Abhängigkeit, im Container problemlos

Dagegen

  • Doppelt so viel Transport-Code, den du pflegst und testest
  • Schema doppelt gepflegt
  • Kein Budget-Limit — nur Turns
  • Kostenschätzung kann stumm ausfallen
  • Verlaufspflege ist die klassische Fehlerquelle
  • Keine eingebauten Tools, kein Freigabe-Gate
11Die Kernfrage

Was kann das SDK mehr

Nicht „müsste man nachbauen“ — sondern das, was fourth_agent.py prinzipiell nicht hat.

Werkzeugkasten

Eingebaute Tools

Read, Grep, Glob, Bash, Datei-Edits. first_agent.py liest eine Projektdatei, ohne dass ein Tool geschrieben wurde. Im Rohbau ist das dein Code — samt Pfad-Absicherung.

Grenze

Freigabeliste

allowed_tools schränkt wirklich ein. comment_checker.py nutzt das ausschliessend: kein Read, kein Bash — das Modell sieht nur zwei Tools. Im Rohbau gibt es nichts zu beschränken, weil es nichts gibt.

Kontext

Projekt als Preset

system_prompt={"type":"preset","preset":"claude_code"} plus cwd zieht CLAUDE.md und die Projektkonventionen herein. Im Rohbau: Dateien selbst finden, lesen, in den Prompt bauen.

Komposition

Subagents als Markdown

dod-checker.md ist Frontmatter (tools:, model: inherit) plus Prompt. Ein Agent, den du schreibst, indem du eine Datei anlegst.

Kostenkontrolle

Hartes Budget

max_budget_usd bricht ab. Im Rohbau erfährst du die Kosten erst hinterher — und nur, wenn die Schätzung für das Modell existiert.

Dauer

Sessions und Kontext

Verwaltung über den einzelnen Lauf hinaus. Im SDK vorhanden, in Modul 5B nicht genutzt — im Rohbau baust du sie gegen dein eigenes messages-Array.

Umgekehrt

Der Rohbau kann eines, was das SDK nicht kann: den Provider wechseln. Für LearnFlow ist das kein Detail, sondern ADR-004.

12Fazit

Beides — nur nicht am selben Ort

Produktivcode · src/backend

Der Rohbau

LiteLLM ist die Schicht, die LearnFlow laut ADR-004 ohnehin fährt: MVP OpenAI Direct → Prod Azure OpenAI EU. Der Wechsel des Providers ist dort eine Anforderung, kein Komfort.

Entwickler-Werkzeuge · am Repo

Das SDK

comment_checker.py als Pre-Commit-Hook, dod-checker vor dem PR. Genau dort machen die eingebauten Tools, die Freigabeliste und der Projektkontext den Nutzen aus.

Und über beidem steht dieselbe unveränderte confidence.py.

Die interessantere Architektur ist ohnehin comment_checker.py: Python entscheidet, was eindeutig ist — gratis und deterministisch; das Modell nur die Zweifelsfälle. Bei sauberem Staging läuft kein Modell. Diese Arbeitsteilung gilt unabhängig davon, ob darunter das SDK oder OpenAI steckt.
