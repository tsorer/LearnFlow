Wie LearnFlow aufgebaut ist

Vier Docker-Container, drei getrennte Netzwerke und genau ein Übergang nach aussen — zum LLM-Provider via LiteLLM. Die Grafik zeigt nicht nur, wer mit wem spricht, sondern auch, wer bewusst nicht direkt miteinander spricht.

edge — Browser ↔ Web App ↔ API api-db — API Server ↔ Datenbank worker-db — Worker ↔ Datenbank gestrichelt — Grenze zum externen LLM-Provider

Synchron · Frage & Antwort

Q&A-Request

  1. Browser sendet POST /api/query, JWT im Header app/routers/query.py
  2. API generiert Query-Embedding → LLM-Provider
  3. Hybrid-Retrieval gegen die DB: pgvector HNSW + Volltext, RRF-Fusion (ADR-007)
  4. Retrieval-Gate: kein Chunk über Schwelle → „Weiss ich nicht", kein LLM-Aufruf
  5. Prompt an LLM-Provider, Antwort generieren
  6. Grounding-Check, ggf. Self-Check bei Grenzfällen (ADR-008, fail-closed)
  7. Batch-Response (JSON) an Browser: Antwort + Quellen + Konfidenz

Asynchron · Hintergrund-Verarbeitung

Dokument-Upload

  1. Stefan lädt Dokument hoch, POST /api/documents app/routers/documents.py
  2. API speichert Datei (bytea, ≤10 MB) + schreibt Job-Zeile, bestätigt sofort
  3. DB benachrichtigt Worker per pg_notify — kein Aufruf durch die API selbst
  4. Worker extrahiert Text, chunked strukturbewusst (~512 Token / 64 Overlap)
  5. Worker embedded jeden Chunk → LLM-Provider
  6. Worker schreibt Chunks + Embeddings zurück, Status → „verfügbar" (SLA: 5 Min. / ≤50 Seiten)
