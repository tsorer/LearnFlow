Wie eine Schwelle aus der Tabelle zur Pipeline wird

read_query_config — der Reader, den jede einzelne Frage durchläuft, bevor überhaupt retrievt wird. Die Regel dahinter ist einfach zu formulieren und leicht falsch zu implementieren: eine fehlende Zeile ist normal, eine kaputte ist ein Notfall — und die beiden dürfen nie dieselbe Behandlung bekommen.

Dieselbe Art Fehler — ein kaputter Konfigurationswert — bekommt drei verschiedene Antworten, weil die Konsequenz jedes Mal eine andere ist: ein Mensch am Formular, eine Antwort an einen Lernenden, oder ein Prozess, der sonst niemand mehr beobachtet.

fail-closed — kein Ersatzwert

Fehlend ist nicht kaputt

Zwei Fälle, die leicht verwechselt werden

  • Eine fehlende Zeile ist der Normalfall — der Default ist genau dafür da, niemand hat je etwas anderes verlangt
  • Eine vorhandene, aber unlesbare Zeile ist das Gegenteil: jemand wollte etwas Bestimmtes, und es ging schief. Dafür gibt es keinen Default, der nicht lockerer wäre als gemeint
  • Migration 0009 weist einen solchen Wert schon beim Schreiben ab, auf beiden Schreibwegen — dieser Reader wirft trotzdem, für den Fall einer Zeile, die am Constraint vorbei entstand (ein Dump von vor 0009, manuelles SQL)

Ein Wert, eine Anfrage

Warum kein Cache

  • Kein Cache: ein per SQL oder Admin-Endpoint geänderter Wert wirkt auf die nächste Anfrage — ein Round-Trip auf zehn Zeilen ist neben dem Embedding-Aufruf, den er schützt, vernachlässigbar
  • Die zwei Bandpaare werden zusätzlich gegeneinander geprüft — ein invertiertes Band ist keine mildere Einstellung, sondern eine leere: kein Score kann gleichzeitig über high und unter low liegen
  • Pipeline-Parameter und Bandgrenzen werden in einem Round-Trip gelesen, weil eine Anfrage ohnehin beide braucht — zwei Abfragen wären zwei zum Preis von einer
