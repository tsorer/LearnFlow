Wie Anmeldung und Rollen-Rechte funktionieren

Zwei getrennte Fragen, die im Code auch getrennt beantwortet werden: wer bist du (routers/auth.py, get_current_user) und was darfst du (require_role, pro Endpoint). Beide sind absichtlich fail-closed — im Zweifel 401/403, nie ein stillschweigendes Durchwinken.

Matrix

Wer darf was

Route learner knowledge_owner admin Hinweis
POST /auth/login ––– öffentlich, kein Token nötig · 5/min pro IP
GET/POST/DELETE /documents ✗ require_knowledge_owner
GET /documents/{id}/content jede Rolle — der Chunk wurde bereits zitiert (T-21)
POST /query 10/min pro Account
POST /answers/{id}/feedback nur wer schreibt wird geprüft — Zeile bleibt pseudonymisiert
GET /feedback (Übersicht) ✗ require_knowledge_owner
GET /quiz/questions learner sieht nur status=approved (Filter engt ein, nie 403)
POST /quiz/generate ✗ 3/min pro Account
PATCH /quiz/questions/{id} ✗ Review-Entscheid (T-35)
GET/PUT /admin/config ✗✗ require_admin — einzige admin-exklusive Gruppe

Die Rollen bilden eine echte Hierarchie, kein Geflecht: jedes Recht von learner hat auch knowledge_owner, jedes davon auch admin — require_knowledge_owner schliesst admin im Code explizit mit ein.

Wiederkehrendes Muster

Existenz nie verraten

  • Gleiches 404 für „existiert nicht" und „gehört dir nicht" — unabhängig voneinander so kommentiert in documents.py (Bereichsprüfung), feedback.py (Antwort-Zugehörigkeit) und quiz.py
  • visible_statuses() engt nur ein, verweigert nie: fragt ein learner nach status=pending, bekommt er eine leere Liste statt 403 — ein Filter bleibt ein Blick auf die eigenen Rechte, keine Berechtigungsanfrage

Rate-Limiting

Zwei verschiedene Schlüssel

  • /auth/login zählt pro IP — es gibt noch keinen Account, gegen den man zählen könnte. Jede geschützte Route danach zählt pro Account, aus dem Token gelesen
  • Grund für den Wechsel: die Pilot-Nutzer sitzen hinter einem gemeinsamen Büro-NAT — ein IP-Limit dort würde ein einzelner Vielfrager für alle sperren (Docs/03_QualityAttributes.md, Security)
