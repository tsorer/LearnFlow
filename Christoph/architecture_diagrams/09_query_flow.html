Was um die Konfidenz-Pipeline herum passiert

Die acht Stufen selbst (Retrieval, Gate, Konfidenz, Generierung, Citation-Check, Band, Self-Check) stehen im Retrieval-Pipeline-Diagramm. Hier geht es um das Drumherum: welche Session eine Frage bekommt, und was von einer Antwort tatsächlich in der Datenbank landet — das ist nicht dasselbe wie das, was der Browser sieht.

Divergenz

Was der Browser sieht, ist nicht, was die Zeile hält

FeldAPI-Antwort (immer sichtbar)answers-Zeile (DB)
citation_coverage 0.0, wenn Stufe 2 nie lief — die Spec führt das Feld nicht-nullable NULL, wenn Stufe 2 nie lief — sonst würde „nie gemessen" als „0 % belegt" in die Kalibrierung (ADR-009) einfliessen
self_check_passed — kein Teil von ConfidenceInfo, nur in debug.stages (admin) NULL, wenn Stufe 3 nie lief (Normalfall) — ein Default false sähe wie eine gescheiterte Prüfung aus
answer_text message — Klartext, bei Unterdrückung der standardisierte „Weiss ich nicht"-Text NULL bei jeder Unterdrückung — die Spalte hält nur, was die Pipeline tatsächlich produziert hat

Alle drei Divergenzen sind absichtlich: eine API-Antwort darf laut Spec kein null führen, aber eine Auswertung über answers muss „nie gemessen" von „als 0 gemessen" unterscheiden können.

Session-Handling

Kulant, mit Absicht

  • Eine unbekannte oder fremde session_id schlägt nie mit 404 fehl — der Vertrag kennt keinen; eine Frage zu beantworten ist nützlicher als eine veraltete Client-ID abzulehnen
  • Fremde IDs werden trotzdem nicht übernommen — eine Session ist der Gesprächsfaden einer Person, kein globaler Schlüssel, den man sich leihen kann

Persistenz ist Vertrag, nicht Log

Warum jede Unterdrückung schreibt

  • Jede der 8 fail-closed-Unterdrückungen schreibt eine echte Answer-Zeile — auch configuration_error, weil answer_id ein Pflichtfeld der Antwort und das FK-Ziel für POST /answers/{id}/feedback ist
  • Ein echter 503 schreibt dagegen nichts — es gibt keinen answer_id, den ein Client später fürs Feedback bräuchte
