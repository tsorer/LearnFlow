Ein Fail-closed-Paar in zwei Hälften (T-42, ADR-005): ein automatischer Guard, der API und Worker beim Start abbrechen lässt, sobald Konfiguration und Datenbank auseinanderlaufen — und ein manuelles Skript, das einzige, was diesen Abbruch je auflöst, weil es dabei den ganzen Korpus neu einbetten muss.

Ein Fail-closed-Paar, zwei Hälften

Automatisch abstürzen, manuell heilen

  • Der Start-Guard ist absichtlich automatisch und ohne Fallback: weder API noch Worker dürfen je einen Chunk unter einer unabgeglichenen Konfiguration einbetten (ADR-008) — ein Absturz ist hier das sichere Verhalten, keine Störung
  • Das Abgleich-Skript ist absichtlich manuell: eine Re-Indexierung des ganzen Korpus ist eine folgenreiche Operation, die keiner der beiden Prozesse je von sich aus während eines Starts auslösen sollte
  • docker compose run statt docker exec: sobald .env den geänderten Wert trägt, crash-loopen die laufenden Container genau an der Abweichung, die das Skript auflösen soll — oft gibt es also gar keinen laufenden Container, in den man exec'en könnte

Warum eine Transaktion für den ganzen Korpus

Alles oder nichts, kein Ausfall

  • Alle Chunks werden sofort gelöscht statt dem Worker überlassen, sie Dokument für Dokument zu ersetzen — bis der letzte Requeue durchläuft, wären sie sonst Vektoren aus zwei verschiedenen Modellen in derselben Suche
  • Freigegebene Quiz-Fragen fallen auf pending zurück, mit derselben Begründung wie bei einer Dokument-Ersetzung (siehe Upload-Flow) — sonst liefe eine genehmigte Frage mit chunk_id NULL weiter aus, verankert in einem Korpus, der gerade unter ihr weggezogen wurde
  • Kein Ausfall nötig: ein Indexierungslauf, der sein Dokument noch vor dem Commit dieses Skripts gelesen hat, verliert einfach den Versions-Wettlauf und verwirft sich selbst als Superseded — derselbe Mechanismus, der auch eine gewöhnliche Dokument-Ersetzung schützt
