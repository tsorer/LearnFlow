Eine falsche Rolle führt zurück auf /, nicht auf /login — der User ist ja angemeldet, eine eigene Fehlerseite für diesen Fall wäre Ballast.

State-Ort ist kein Zufall

Warum Chat-State in App.tsx liegt

  • messages/sessionId/busy liegen in App.tsx, nicht in ChatView — /quiz und /quiz-review unmounten ChatView, lokaler State wäre beim Zurücknavigieren leer (US-09 verlangt die Historie für die ganze Browser-Session)
  • busy gehört bewusst dazu: bliebe es lokal, setzte ein Remount es zurück, während eine alte Anfrage noch läuft und am Ende in die (jetzt gehobenen) messages schreibt — die Sperre gegen eine zweite Frage während des Wartens griffe dann nicht mehr
  • JWT und User nur im Memory (ADR-002), bewusst kein localStorage — dasselbe Prinzip wie im Auth/RBAC-Diagramm auf der Backend-Seite

Guards sind UX, nicht Sicherheit

Die Grenze bleibt serverseitig

  • ProtectedRoute/GuestRoute sind zentral statt pro Route inline — eine neue geschützte Seite kann so nicht versehentlich ohne Guard entstehen
  • Ein Guard hier verhindert nur, dass die UI eine Seite zeigt, die der Server ohnehin mit 403 abweisen würde — die eigentliche Durchsetzung bleibt in require_role (siehe Auth/RBAC-Diagramm)
  • Drei verschiedene Fehlerformen (eigene HTTPException, FastAPI-Validierungsliste, nginx-Klartext bei 413/502) laufen in errorMessage() zu einem einzigen anzeigbaren String zusammen
