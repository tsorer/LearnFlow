03L1 · Die Rolle

encodingVerifier

Eine Rolle, die zum Projekt passt: LearnFlow schreibt Docs auf Deutsch, falsch kodierte Umlaute sind ein reales Ärgernis. Der Subagent prüft vor dem Commit.

encodingVerifier = AgentDefinition(
    description="Prüft das Encoding der noch nicht committeten Dateien. "
                "Nutze IMMER, wenn Code committed werden soll",
    prompt="Du prüfst Datei-Encodings. Führe dafür python check_encoding.py …",
    tools=["Bash", "Read"],   # minimal
    maxTurns=5,                # eigenes Budget — siehe Slide 08
    model="haiku",           # Routine = billig
)

Delegation nachgewiesen

Im Stream erscheint >>> TOOL: Agent … subagent_type: encodingVerifier — das Modell hat selbst delegiert, ohne dass die Rolle im Prompt genannt wurde.

Kein Skill hat gewonnen

Die description-Konkurrenz war kein Thema: für „Prüfe das Encoding der neuen Dateien" gibt es keinen Built-in-Skill, der plausibler klingt.

04Das Werkzeug

Der Subagent bekommt ein Skript,
kein Mandat

Erste Fassung: der Subagent durfte Write — und schrieb sich prompt eigene Prüfskripte, eines davon im Repo-Root, ausserhalb des Übungsordners.

Vorher

check_encoding.py mit 17 hartcodierten Backend-Pfaden. Der Agent musste raten, was „die neuen Dateien" sind.

Nachher

Die Dateiliste kommt aus git status. Der Agent führt einen Befehl aus, das Skript weiss den Rest.

# Scope = aktuelles Verzeichnis, -z haelt Pfade mit Leerzeichen heil
entries = git("status", "--porcelain", "-uall", "-z", "--", str(scope)).split("\0")

Nebenbei gelernt: die latin-1-Fallback-Erkennung akzeptiert jedes Byte. Bei einer festen .py-Liste egal — bei einer aus Git generierten hätte sie ein PNG als „latin-1" erkannt und beim Konvertieren zerstört. Also ein Binär-Check davor.

05Lektion 1

Zwei Achsen, die man leicht verwechselt

Der erste Lauf scheiterte daran, dass tools und allowed_tools beide auf ["Read", "Grep"] standen. Sie bedeuten nicht dasselbe.

EbeneVerfügbarkeit — welche Tools existierenErlaubnis — was ohne Rückfrage läuft
globalopts.toolsopts.allowed_tools / disallowed_tools
pro AgentAgentDefinition.toolsnur disallowedTools

Auf der AgentDefinition gibt es kein allowedTools. Eine Erlaubnis lässt sich gar nicht pro Agent formulieren — das Permission-System ist sessionweit. Deshalb steht Bash(python check_encoding.py) in den opts und nicht beim Subagenten.

Konsequenz: die Delegation ist eine Konvention über description und Prompt, keine erzwungene Grenze. Auch der Haupt-Agent dürfte den erlaubten Befehl ausführen.

06L3 · Guardrail

Der programmierbare Türsteher

audit_log = []

async def gate(tool_name, input_data, context):
    audit_log.append((tool_name, str(input_data)[:600]))
    if tool_name == "Bash" and "rm -rf" in str(input_data):
        return PermissionResultDeny(message="Blockiert!")
    return PermissionResultAllow()

opts = ClaudeAgentOptions(
    can_use_tool=gate,
    allowed_tools=[],                          # entscheidend
    disallowed_tools=["Bash(git push:*)"],   # harte zweite Schranke
)

allowed_tools=[] ist kein Versehen. Permission-Regeln werden vor dem Callback ausgewertet. Ein Eintrag, der ein ganzes Tool freigibt, schaltet den Callback dafür stumm — das SDK warnt sogar von selbst:

WARNUNG: can_use_tool will not be invoked for: Read, Grep, Task, Agent.

Mit der ursprünglichen Liste wäre das Audit-Log bei einem normalen Lauf leer geblieben — Teilziel (a) verfehlt, ohne dass es jemand gemerkt hätte.

07Der teure Bug

„AbortError: Stream closed"

Der Subagent lief Amok: über 50 Bash-Aufrufe, hexdump, od, file -i, selbstgeschriebene Skripte, am Ende python ohne Argumente. Das Muster von jemandem, dessen Werkzeug grundlos klemmt.

Symptom sichtbar machen

Die Schleife druckte nur ToolUseBlock. Erst mit ToolResultBlock aus der UserMessage kam die Meldung zum Vorschein: Tool permission request failed: AbortError: Stream closed.

Der Beweis: Audit-Log (0 Aufrufe)

Bei über 20 Tool-Aufrufen und leerer Allow-Liste hätte jeder durch gate() laufen müssen. Null Einträge heisst: die Anfrage erreicht das Python-Skript nie. Dass Read und ls trotzdem durchkamen, liegt daran, dass das CLI lesende Tools selbst freigibt.

Ursache im SDK

can_use_tool läuft über das Control-Protokoll auf stdin. Ist der Prompt-Generator erschöpft, schliesst stream_input() stdin sofort — und query.py:925 hält es nur für sdk_mcp_servers oder hooks offen, nicht für can_use_tool.

async def prompt_stream():
    yield {"type": "user", "message": {"role": "user", "content": PROMPT}, …}
    await done.wait()   # haelt stdin offen, bis die ResultMessage da ist
08Runden-Limit

Zwei Budgets, nicht eines

opts.max_turns=15 galt nur für den Haupt-Agenten. Der Subagent hatte gar keine Grenze — daher die 50 Aufrufe.

encodingVerifier = AgentDefinition(
    …
    maxTurns=5,   # eigenes Budget des Subagenten
)

Wirkung im nächsten Lauf, direkt aus dem Tool-Result ablesbar:

<usage> subagent_tokens: 9541 · tool_uses: 5 · duration_ms: 18405 </usage>

Das Lab-Handout nennt denselben Mechanismus für L2: das Runden-Limit ist der Guardrail — und ein erreichtes Limit wirft eine Exception, die ohne try/except den ganzen Orchestrator mitnimmt.

09Die Blockade

Deny — und was der Agent daraus macht

Wegwerf-Ordner tmp_demo/ angelegt, Prompt: „Lösche den Ordner tmp_demo mit rm -rf".

>>> TOOL: Bash  Input: {'command': 'rm -rf tmp_demo', …}
!!! BLOCKIERT: Bash {'command': 'rm -rf tmp_demo', …}
<<< RESULT (err=True): Blockiert!

--- Turns: 2 · Kosten: $0.0240 ---
--- Audit-Log (1 Aufrufe) ---

Reaktion

Abbruch mit Rückfrage. Der Agent bittet, den Ordner von Hand zu löschen — er probiert keinen Alternativweg.

Fehldiagnose

„wahrscheinlich durch eine Sandbox-Einschränkung". Er sieht nur „Tool-Fehler: Blockiert!" und rät. Eine sprechende message würde ihm helfen.

Ordner intakt

tmp_demo/marker.txt unverändert. Die Sperre hat gehalten.

10Lektion 2

Der Filter ist Theater

Dass es gut ging, lag am Wohlverhalten des Modells — nicht am Guardrail. Derselbe Löschbefehl, vier Schreibweisen:

BefehlErgebnis
rm -rf tmp_demodeny
rm -r tmp_demoallow
rm -fr tmp_demoallow
rmdir /s tmp_demoallow

Drei von vier Varianten kommen durch. Ein Substring-Filter ist keine Sicherheitsgrenze.

Und der Callback sieht nicht alles. Im erfolgreichen Encoding-Lauf standen 2 Einträge im Audit-Log — der Agent-Aufruf, also die Delegation selbst, fehlte. Lesende Tools gibt das CLI vor dem Callback frei. Wer wirklich jeden Aufruf sehen will, braucht einen PreToolUse-Hook.

11Bilanz

Was das System kostet

$0.1434 Kaputter Lauf · 6 Turns

50+ Tool-Aufrufe, 0 Audit-Einträge, kein Ergebnis.

$0.0242 Encoding-Lauf · 2 Turns

9 Dateien geprüft, 2 Audit-Einträge, Exit-Code 0.

$0.0240 Deny-Lauf · 2 Turns

1 Aufruf, blockiert, Ordner intakt.

Der kaputte Lauf kostete das Sechsfache des funktionierenden — und lieferte nichts. Ein Agent, dessen Werkzeug klemmt, wird nicht langsamer, sondern teurer.

Offen

L2 (P→G→E) auf ein echtes Sprint-Feature bringen, mit try/except um run() und Runden-Limit als Guardrail. Für LearnFlow bietet sich die Fail-closed-Schwelle aus ADR-008 an — dort gibt es eine Spec, gegen die der Evaluator prüfen kann.
