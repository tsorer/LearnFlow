## Code Review: `math_utils.py`

### 🔴 Kritische Probleme

**1. Zirkulärer Self-Import (Z. 23)**
```python
from math_utils import MathUtils  # ← Datei importiert sich selbst
```
Das führt bei jedem Import zu einem `ImportError` oder unendlicher Rekursion. Die Demo-/Nutzungslogik (Z. 23–36) gehört **nicht** in dieselbe Datei wie die Klasse. Entweder in einen `if __name__ == "__main__":`-Block oder in eine separate Datei.

**2. Fehlerbehandlung `divide` ist irreführend (Z. 18–19)**
```python
if b == 0:
    return -1.0  # Handle division by zero
```
`-1.0` ist ein gültiges Rechenergebnis — ein Aufrufer kann nicht unterscheiden, ob die Division erfolgreich war oder ein Fehler auftrat. Korrekte Python-Konvention:
```python
raise ZeroDivisionError("division by zero")
```

---

### 🟡 Mittlere Probleme

**3. Keine Typ-Annotationen**
Die Methoden haben keine Type Hints. Dadurch gibt es keine statische Prüfung (z. B. mit `mypy`):
```python
# Statt:
def add(self, a, b):
# Besser:
def add(self, a: float, b: float) -> float:
```

**4. Shadowen von Builtins (Z. 28)**
```python
sum = math_utils.add(5, 3)  # überschreibt das eingebaute sum()
```
Variablenname `sum` sollte umbenannt werden, z. B. `result_sum`.

**5. Klasse ist unnötig (Stateless)**
`MathUtils` hat keinen Zustand — alle Methoden könnten einfache Modul-Funktionen sein. Die Klasse fügt Komplexität hinzu ohne Nutzen. Alternativ `@staticmethod` oder `@classmethod` verwenden, wenn eine Klasse gewünscht ist.

---

### 🟢 Positives

- Docstrings vorhanden und verständlich
- `divide` erkennt den Nullfall (auch wenn die Lösung falsch ist)
- Logik der vier Grundoperationen selbst ist korrekt
